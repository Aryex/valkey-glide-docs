---
title: Cluster Awareness
---

Valkey GLIDE was designed to handle the complexities of Valkey (and Redis) clusters automatically.
It abstracts away slot management, node discovery, and failover logic so your application interacts with the cluster as if it were a single endpoint.

For information on Valkey Cluster, see this [page](https://valkey.io/topics/cluster-tutorial/).

## Topology Aware

Requiring only one initial node within a cluster, GLIDE can use it to discover out the full topology and hash slot ownership.
This allows GLIDE to calculates the destination of every command before sending it, ensuring they go directly to the correct
node rather than bouncing around the cluster.
If the cluster topology changes, either due to scaling or failover, GLIDE will automatically update its internal mapping.

### Hash Slot

Valkey has a total of 16,384 fixed slots from which it splits across nodes in a cluster. Each key are then assigned to a slot for storage.
GLIDE's mapping of the cluster allows it to send them to the appropriate node.

## Multi-Key Commands Handling

Valkey (and Redis) clusters support commands that operate on multiple keys which maybe spread across different hash slot.
GLIDE cluster awareness allows it to efficiently handles these commands, ensuring correct executions across the cluster.

To learn more about multi-key commands, see this [section](/concepts/client-features/multi-slot-command-handling/).

## Redirect Handling

When the cluster topology changes or a slot migrates to a different node, the server returns a MOVED error directing the client to the correct node.
GLIDE automatically follows these redirects and refreshes its internal slot map so subsequent commands route correctly without any application-level intervention.

### Circular MOVED Redirects

When Valkey servers are deployed behind DNS records, load balancers, or proxies, a MOVED error may point back to the same endpoint the client is already connected to.
This creates a "circular" redirect — previously, this could cause commands to fail because the connection was already closed by the server after sending the MOVED response.

GLIDE now automatically detects circular MOVED redirects and triggers a connection refresh before retrying the command.
This allows the DNS, proxy, or load balancer to route the new connection to a different underlying server, resolving the redirect.

This behavior:

- Applies to both single commands and pipeline commands.
- Handles hostname/IP mismatches (e.g., connected via hostname but MOVED returns an IP address).
- Requires no configuration — it is entirely automatic.
